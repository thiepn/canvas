# Phase 1 — diagnostics and performance baseline

Phase 1 is observational. It does not change Canvas synchronization semantics, conflict resolution, persistence rules, or the visible tool set.

## Local diagnostics

Open the normal Excalidraw + Supabase Canvas with `?debug=1` to enable a local-only diagnostics overlay. Normal sessions pay only the module/code cost; sampling remains disabled unless explicitly requested.

The overlay and `window.__CANVAS_DIAGNOSTICS__.snapshot()` report rolling measurements for:

- frame duration, approximate FPS, and frames over 50 ms;
- authoritative Canvas rows observed and current active-element count;
- in-flight durable write depth;
- Supabase REST write latency, write-batch count, rows sent, and failures;
- initial Live synchronization and reconnect duration;
- incoming Postgres Realtime messages to the next animation frame;
- durable write batches attributable to a pointer gesture;
- JavaScript heap where the browser exposes it.

`window.__CANVAS_DIAGNOSTICS__.reset()` clears only local counters/samples. Diagnostics never send telemetry to an analytics endpoint and never record element contents.

## Reproducible benchmark

`npm run test:performance` runs Chromium against Vite `performance` mode and the real Excalidraw package. The 100 / 1,000 / 5,000 / 10,000-element scale fixtures exist only inside an isolated Excalidraw harness; they are never written to Supabase.

For each fixture, the benchmark measures fixture generation, initial rendering, serialization, pan frame timing, one-element movement, twenty-element movement, twenty-element selection, payload size, and Chromium heap usage.

A separate two-client test uses `canvas_ci_elements` and the normal `SupabaseCanvasEditor` to measure:

- time for two clients to reach Live;
- a real rectangle gesture on client A until pixels change on client B;
- durable Supabase write latency and write volume;
- incoming Realtime-to-frame timing;
- writes generated by the measured pointer gesture;
- offline-to-Live reconnect timing.

The CI table is cleaned before and after the measurement. Production `canvas_elements` is not modified.

## Evidence

Run:

```bash
npm run test:performance
npm run performance:report
```

The manual `Canvas performance evidence` GitHub workflow executes the benchmark in a version-pinned Playwright Chromium container and retains:

- `artifacts/performance.json` — machine-readable measurements;
- `artifacts/performance-baseline.md` — generated human-readable report;
- `artifacts/performance-run.json` — Playwright evidence;
- failure traces/screenshots when applicable.

The first run is a baseline, not a target. Later phases should compare equivalent runs and should not retroactively choose thresholds that make an implementation look successful.
